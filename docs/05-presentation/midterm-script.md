
# 클라우드 기반 ESG 데이터 관리 플랫폼 중간발표 대본

## 1. 표지

안녕하세요.
클라우드 기반 ESG 데이터 관리 플랫폼 중간발표를 시작하겠습니다.

저희 팀은 팀장 김성민, 팀원 박정은, 홍현민, 조성민으로 구성되어 있습니다.

이번 프로젝트에서는 기업의 환경, 사회, 거버넌스 데이터를 수집하는 것에서 끝나는 것이 아니라, 데이터 검증과 승인 과정을 거쳐 신뢰할 수 있는 공식 ESG 실적으로 관리하는 플랫폼을 구현하고 있습니다.

발표는 프로젝트 개요, 사용 기술, 사용자 권한, 업무 흐름, 시스템 아키텍처와 ERD, 배포 설계, 시연 시나리오, 향후 계획 순서로 진행하겠습니다.

---

## 2. 프로젝트 개요

먼저 ESG의 의미와 저희가 이 플랫폼을 만들게 된 배경을 설명드리겠습니다.

ESG는 환경을 의미하는 Environment, 사회를 의미하는 Social, 그리고 거버넌스를 의미하는 Governance의 약자입니다.

환경 영역에서는 전력 사용량, 온실가스 배출량, 폐기물과 같은 기업의 환경 영향을 관리합니다.

사회 영역에서는 산업재해율, 안전교육 이수율, 위험요인 개선 조치율, 퇴사율과 같이 근로자와 안전에 관련된 지표를 관리합니다.

거버넌스 영역에서는 이사회 참석률, 사외이사 비율, 윤리교육 이수율과 같이 기업의 투명성과 책임경영 수준을 관리합니다.

ESG 관리는 단순히 보고서를 한 번 작성하는 것이 아니라, 기업 활동을 측정 가능한 데이터로 남기고 그 데이터가 정확한지 검증하는 과정이라고 볼 수 있습니다.

하지만 실제 기업에서는 EMS, 인사시스템, 안전관리시스템, 그룹웨어처럼 데이터가 여러 시스템에 분산되어 있습니다. 또한 담당자가 확인 중인 잠정 데이터와 최종 승인된 확정 데이터가 섞일 경우, 대시보드나 보고서 수치의 신뢰성이 떨어질 수 있습니다.

저희는 이 문제를 해결하기 위해 원천 데이터를 월별로 수집하고, 검증과 AI 분석을 거친 뒤, 담당자가 승인 요청을 하고 시스템 관리자가 최종 승인하도록 설계했습니다.

그리고 최종 승인된 데이터만 공식 대시보드와 보고서에 반영되도록 구현했습니다.

현재 중간 구현 단계에서는 환경, 사회, 거버넌스 월별 데이터와 AI 분석, 승인 요청, 최종 승인 흐름을 구성했으며, Docker와 AWS를 활용한 배포 구조도 함께 설계했습니다.

## 3. 사용 기술과 선택 이유

다음은 프로젝트에 사용한 주요 기술입니다.

프론트엔드는 React와 Vite를 사용했습니다.
React는 화면을 컴포넌트 단위로 나누어 관리할 수 있고, Vite는 개발 서버와 빌드 속도가 빠르기 때문에 화면을 빠르게 구현하고 수정하는 데 적합했습니다.

백엔드는 Java 17과 Spring Boot를 사용했습니다.
Spring Boot는 REST API, 인증과 권한, 데이터 검증, 예외처리와 같은 서버 기능을 안정적으로 구성할 수 있다는 장점이 있습니다.

데이터베이스는 PostgreSQL을 사용했습니다.
ESG 원천 데이터, 계산 결과, 승인 상태, 처리 이력, 보고서 정보와 같이 장기간 보존해야 하는 데이터를 영구 저장하는 역할을 합니다.

Redis는 PostgreSQL과 역할이 다릅니다.
Refresh Token과 로그아웃된 Access Token, 대시보드 캐시, 데이터 수집 중복 실행을 막기 위한 분산락, AI 분석 진행 상태처럼 빠르게 조회해야 하거나 일정 시간이 지나면 삭제해도 되는 데이터를 저장합니다.

MyBatis는 SQL을 직접 확인하고 관리하기 위해 사용했습니다.
ESG 데이터는 월별 집계나 상태별 조회처럼 SQL 조건이 비교적 명확하기 때문에 MyBatis가 적합하다고 판단했습니다.

Flyway는 데이터베이스 변경 이력을 관리하기 위해 사용했습니다.
현재 V1부터 V5까지 마이그레이션 파일을 순서대로 적용하여 팀원 모두가 같은 테이블 구조를 사용할 수 있도록 구성했습니다.

Docker는 팀원별 실행 환경 차이를 줄이기 위해 사용하고 있으며, 최종적으로는 AWS EC2에서 컨테이너 형태로 배포할 계획입니다.

즉, 기술 선택의 기준은 빠른 개발, 팀 환경 통일, 데이터베이스 변경 이력 관리, 그리고 클라우드 배포 확장성입니다.

## 4. 사용자 권한 구조

저희 플랫폼은 세 가지 사용자 권한으로 구성되어 있습니다.

첫 번째는 기업 ESG 관리자인 `COMPANY_MANAGER`입니다.

기업 ESG 관리자는 EMS, 인사, 안전, 그룹웨어에서 수집된 데이터를 확인하고 수정할 수 있습니다. 또한 증빙자료를 등록하고 AI 분석을 실행한 뒤, 검토가 완료된 데이터에 대해 승인 요청을 보냅니다.

두 번째는 시스템 총괄 관리자인 `SYSTEM_ADMIN`입니다.

시스템 총괄 관리자는 기업 ESG 관리자가 요청한 데이터를 검토하고 최종 승인하거나 반려합니다. 이외에도 기업, 사용자, ESG 지표, 외부 시스템 연동 상태 등을 관리합니다.

세 번째는 일반 사용자인 `EXTERNAL_USER`입니다.

일반 사용자는 최종 승인된 ESG 실적과 공개 보고서만 조회할 수 있습니다. 승인 전 데이터나 담당자가 검토 중인 잠정값은 볼 수 없습니다.

이렇게 권한을 분리한 이유는 데이터 작성자와 승인자를 구분하기 위해서입니다.

기업 ESG 관리자가 데이터를 작성하고, 시스템 총괄 관리자가 최종 승인하며, 일반 사용자는 확정된 결과만 조회하게 함으로써 데이터의 신뢰성과 책임 소재를 명확하게 했습니다.

## 5. 업무 흐름도

다음은 플랫폼의 전체 업무 흐름입니다.

이 슬라이드는 왼쪽에서 오른쪽 방향으로 보시면 됩니다.

가장 먼저 EMS, 인사, 안전, 그룹웨어와 같은 외부 시스템에서 데이터가 생성됩니다.

이 데이터는 스케줄러를 통해 월별로 자동 수집되며, PostgreSQL에 원천 데이터로 저장됩니다.

기업 ESG 관리자가 로그인하면 자신이 담당하는 기업과 사업장 정보를 확인하고, 원하는 기준연도의 월별 데이터를 조회할 수 있습니다.

수집된 데이터는 환경, 사회, 거버넌스 영역으로 나누어 처리됩니다.

환경 영역에서는 전력 사용량과 생산량을 기준으로 원단위와 Scope 2 배출량을 계산합니다.

사회 영역에서는 산업재해율, 안전교육 이수율, 위험요인 개선 조치율, 퇴사율을 계산합니다.

거버넌스 영역에서는 이사회 참석률, 사외이사 비율, 윤리교육 이수율을 계산합니다.

계산된 데이터는 바로 공식 수치가 되는 것이 아니라, 먼저 ESG 업무 데이터로 반영됩니다.

이후 AI 분석을 통해 누락값이나 이상치, 위험요인 또는 문서 내용을 검토하고 기업 ESG 관리자가 승인 요청을 합니다.

시스템 총괄 관리자는 승인 대기 데이터를 확인하고 최종 승인 또는 반려합니다.

반려된 경우에는 기업 ESG 관리자가 수정한 후 다시 요청하며, 승인된 경우에는 공식 대시보드와 보고서에 반영됩니다.

일반 사용자는 이 최종 승인 데이터만 조회할 수 있습니다.

전체 업무 흐름을 요약하면 **수집, 조회 및 반영, 승인, 공개**의 네 단계입니다.

## 6. 시스템 아키텍처

다음은 시스템 아키텍처입니다.

가장 위쪽은 사용자 화면인 Client 영역입니다.

일반 사용자, 기업 ESG 관리자, AI 분석 화면, 시스템 총괄 관리자 화면을 React와 Vite 기반의 SPA 구조로 구현했습니다.

프론트엔드에서는 Axios를 통해 Spring Boot의 REST API를 호출합니다.

중앙의 Application Server는 Spring Boot로 구성되어 있습니다.

먼저 Controller Layer에서는 인증, 기업과 사업장, 환경, 사회, 거버넌스, 대시보드, 보고서, 승인, 사용자 관리 등의 API 요청을 받습니다.

그 아래 Service Layer에서는 실제 비즈니스 로직을 처리합니다.

예를 들어 환경 서비스에서는 전력 사용량을 기준으로 Scope 2를 계산하고, 승인 서비스에서는 현재 상태에서 승인 요청이 가능한지 확인하며, 사용자와 권한 서비스에서는 접근 가능한 메뉴와 기능을 제어합니다.

Repository와 Mapper Layer에서는 MyBatis를 사용하여 PostgreSQL과 데이터를 주고받습니다.

오른쪽의 공통 기능에는 Spring Security와 JWT 인증, 카카오 OAuth 로그인, 이메일 인증, Redis 토큰 관리, 대시보드 캐시, 스케줄러 분산락, 공통 예외처리, 유효성 검증, 파일 저장소 연동, SLF4J 로그가 포함됩니다.

하단의 PostgreSQL에는 ESG 원본 데이터와 계산 결과, 승인 이력, 보고서, 감사 로그를 영구 저장합니다.

Redis에는 Refresh Token, Access Token 블랙리스트, 대시보드 캐시, 수집 스케줄러 락, AI 처리 상태를 저장합니다.

외부 서비스로는 Gmail SMTP, 카카오 OAuth, AI 또는 OCR 서비스, 공공데이터 파일, AWS S3와 EC2 등을 연동할 수 있도록 구성했습니다.

전체적으로 프론트엔드, 백엔드, 데이터베이스, 캐시와 외부 서비스를 분리하여 각 영역의 책임이 명확하도록 설계했습니다.

## 7. 핵심 ERD

다음은 Flyway V1부터 V5까지 반영한 핵심 ERD입니다.

ERD는 테이블이 많기 때문에 모든 컬럼을 하나씩 설명하기보다는 주요 영역과 관계를 중심으로 설명드리겠습니다.

먼저 기준 조직과 사용자 영역에는 기업, 사업장, 부서, 사용자 테이블이 있습니다.

기업 한 곳은 여러 사업장을 가질 수 있고, 사업장과 기업을 기준으로 부서와 사용자가 연결됩니다.

다음은 월별 ESG 수집과 승인 영역입니다.

`integration_runs` 테이블에는 외부 시스템 수집 작업 한 번에 대한 실행 이력이 저장됩니다.

`integration_raw_data`에는 외부 시스템으로부터 받은 원본 데이터가 저장됩니다.

그다음 환경, 사회, 거버넌스 월별 테이블에는 기업과 사업장별로 계산된 월간 ESG 데이터가 저장됩니다.

이 데이터는 AI 분석 결과 테이블과 승인 이력 테이블로 연결됩니다.

승인 이력에는 승인 요청, 반려, 재요청, 최종 승인과 같은 상태 변경이 누적 저장됩니다.

ESG 상세 업무 데이터 영역에는 환경 지표 데이터, 제품 탄소발자국, 유해물질 관리, 산업안전 기록, 이사회 구성원과 회의 정보, ESG 목표와 점수 등이 포함됩니다.

기준정보 영역에는 ESG 지표, 업종별 지표 매핑, 배출계수, 한전 요금 기준, 공통코드 등이 있습니다.

예를 들어 전력 사용량을 Scope 2로 계산할 때는 해당 연도의 배출계수 정보를 참조하도록 구성했습니다.

마지막으로 보고서와 감사 영역에는 보고서 템플릿, 생성 보고서, 넷제로 활동, 감사 로그 테이블이 있습니다.

이 ERD의 핵심은 단순히 최종 수치만 저장하는 것이 아니라, 원본 데이터부터 계산 결과, AI 분석, 승인 상태, 보고서와 감사 이력까지 추적할 수 있도록 연결한 것입니다.

## 8. Docker·AWS 배포 설계

다음은 Docker와 AWS 배포 설계입니다.

현재 로컬 개발 단계에서는 React 프론트엔드와 Spring Boot 백엔드를 각자의 개발환경에서 실행하고, PostgreSQL과 Redis는 Docker 컨테이너로 실행할 수 있도록 구성하고 있습니다.

이를 통해 팀원마다 데이터베이스나 Redis 버전이 달라 발생하는 문제를 줄일 수 있습니다.

소스코드는 GitHub에서 관리하고 있으며, 기능 브랜치에서 작업한 후 `develop` 브랜치로 Pull Request를 보내는 방식을 사용합니다.

첫 번째 배포 단계에서는 AWS EC2 인스턴스 한 대에 Docker Compose를 사용해 전체 서비스를 실행할 계획입니다.

Frontend 컨테이너는 React 빌드 결과물을 Nginx를 통해 제공합니다.

Backend 컨테이너는 Spring Boot REST API를 실행합니다.

PostgreSQL 컨테이너에는 ESG 업무 데이터를 영구 저장하고, Redis 컨테이너는 인증과 캐시, 분산락 기능을 담당합니다.

사용자가 브라우저로 접속하면 Nginx가 정적 파일을 전달하고, `/api` 요청은 Spring Boot 백엔드로 전달합니다.

학습과 시연 목적에서는 EC2 한 대에 전체 컨테이너를 구성하는 방식으로 충분합니다.

이후 운영 규모가 커질 경우 PostgreSQL은 Amazon RDS로, Redis는 ElastiCache로, 증빙 파일과 PDF 보고서는 S3로 분리할 수 있습니다.

또한 DB 비밀번호, JWT 비밀키, OAuth Client Secret과 같은 값은 소스코드에 직접 작성하지 않고 환경변수로 분리합니다.

## 9. 시연 시나리오

다음은 중간발표 시연 시나리오입니다.

시연은 총 여섯 단계로 진행됩니다.

첫 번째로 기업 ESG 관리자 계정으로 로그인합니다.

두 번째로 환경 데이터 화면에서 2026년 6월 데이터를 조회합니다.

시연 데이터는 1월부터 5월까지는 이미 승인 완료된 상태이고, 6월은 원천 데이터 수집은 완료되었지만 ESG에는 아직 반영되지 않은 상태로 구성했습니다.

세 번째로 ESG 반영을 실행합니다.

이때 사업장별 전력 사용량을 이용하여 Scope 2와 환경 지표를 산정하고 ESG 업무 데이터로 저장합니다.

네 번째로 AI 분석을 실행합니다.

AI 분석을 통해 데이터 누락이나 이상치를 확인하고, 검토가 끝나면 시스템 총괄 관리자에게 승인 요청을 보냅니다.

다섯 번째로 시스템 총괄 관리자 계정으로 전환하여 승인 대기 데이터를 확인합니다.

데이터에 문제가 없다면 최종 승인하고, 수정이 필요한 경우 반려할 수 있습니다.

여섯 번째로 대시보드에 다시 접속합니다.

최종 승인 전에는 6월 데이터가 공식 통계에 포함되지 않지만, 승인 후에는 6월 데이터가 대시보드와 보고서에 추가되는 것을 확인할 수 있습니다.

이번 시연의 핵심은 단순한 화면 전환이 아니라, 데이터 상태가 실제 데이터베이스에 저장되고 승인 여부에 따라 공식 통계가 달라지는 과정을 보여주는 것입니다.

## 10. 향후 계획

마지막으로 향후 계획입니다.

첫 번째는 데이터 신뢰성 강화입니다.

수집된 ESG 값이 어떤 외부 시스템과 원본 데이터에서 생성되었는지 추적할 수 있도록 연결 정보를 보강하고, 검증 사유와 처리 이력을 더 상세히 기록할 계획입니다.

또한 최종 승인된 데이터는 일반 담당자가 임의로 수정할 수 없도록 제한할 예정입니다.

두 번째는 보고서 기능 고도화입니다.

PDF 보고서의 디자인을 개선하고, 내부 검토용과 외부 공개용 템플릿을 분리하며, 연도별 실적을 비교할 수 있도록 구현할 계획입니다.

세 번째는 AI 분석 기능 보강입니다.

증빙 문서 OCR, 이사회 회의록 분석, 위험요인 자동 분류, 이상치 탐지 규칙 등을 추가할 예정입니다.

다만 AI 결과를 바로 확정값으로 사용하지 않고, 반드시 담당자가 확인한 후 승인 절차를 거치도록 할 것입니다.

네 번째는 운영 안정화입니다.

외부 시스템 수집에 실패했을 때 재처리할 수 있는 기능과 오류 알림, 감사 로그, 권한별 예외처리를 강화하겠습니다.

다섯 번째는 배포 테스트입니다.

프론트엔드, 백엔드, PostgreSQL, Redis를 Docker Compose로 통합 실행하고, AWS EC2에서 실제 접속할 수 있도록 배포 과정을 검증할 계획입니다.

저희의 최종 목표는 단순히 ESG 화면을 구현하는 것이 아닙니다.

원천 데이터의 수집부터 계산, 검증, 승인, 감사 이력, 대시보드와 보고서 공개, 클라우드 배포까지 연결되는 실무형 ESG 데이터 관리 플랫폼을 완성하는 것입니다.

이상으로 발표를 마치겠습니다.
감사합니다.
