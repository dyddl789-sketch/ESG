# 클라우드 기반 ESG 데이터 관리 플랫폼 - 최종발표 대본

## 1. 표지
안녕하십니까, 프로젝트 최종발표를 맡은 팀장 김성민입니다.  
저희가 발표할 주제는 "클라우드 기반 ESG 데이터 관리 플랫폼"입니다.

이 플랫폼은 기업의 환경, 사회, 거버넌스 데이터를 한곳에서 수집하고, 검토와 승인을 거쳐 대시보드와 보고서에 반영하는 시스템입니다.  
팀장 김성민을 포함해 박정은, 홍현민, 조성민 총 4명이 7월 7일부터 21일까지 프로젝트를 진행했습니다.  
지금부터 최종 결과를 발표하겠습니다.

## 2. 목차
발표는 먼저 팀 소개와 프로젝트 개요를 말씀드린 뒤, 일정과 기술 스택, 시스템 설계 자료를 설명드리겠습니다.  
이후 시스템 관리자, 기업 관리자, 일반 사용자 순서로 주요 화면을 소개하고, 핵심 구현 코드와 트러블슈팅, 사후평가 및 팀 회고로 마무리하겠습니다.  

## 3. 팀 소개
저희 팀은 네 명이 기능 영역을 나누어 개발했습니다.  

김성민은 공용 대시보드와 E·S·G 실적 화면, 외부 데이터 비교 및 집계 로직을 담당했습니다.  
박정은은 사용자·권한, 기업·사업장, 지표 관리와 공개 화면을 맡았습니다.  
홍현민은 ESG 데이터 등록과 승인, 감사 로그, 문서 AI 분석 및 인프라를 담당했고,  
조성민은 연동 모니터링, 실적 조회, 리포트 빌더와 문서화를 맡았습니다.  

기능은 나누어 개발했지만, 승인 상태와 데이터 구조처럼 서로 연결되는 부분은 공통 규칙을 정해 지속적으로 맞춰갔습니다.

## 4. 프로젝트 개요
프로젝트의 대상은 가상의 자동차 부품 제조기업인 에코모빌리티 파츠 주식회사입니다.  

본사와 각 사업장의 ESG 실적을 월별로 관리하고, 담당자가 데이터와 증빙을 등록하면 시스템 관리자가 검토해 최종 승인하는 구조로 설계했습니다.  
승인된 데이터는 내부 ESG 지수와 대시보드, 지속가능경영보고서에 활용됩니다.

환경 영역은 전력 사용량, 출하액, Scope 2 배출량을 관리하고,  
사회 영역은 산업재해율, 안전교육 이수율, 위험요인 개선 조치율, 퇴사율을 관리합니다.  
거버넌스 영역은 이사회 참석률, 사외이사 비율, 윤리교육 이수율을 관리합니다.

전체 30개 화면을 프로그램 ID 체계로 구분해 개발했고, 데이터베이스 변경 이력은 Flyway로 관리했습니다.

## 5. 프로젝트 일정
전체 프로젝트 기간은 총 15일입니다.

초반에는 요구사항과 화면 흐름, ERD를 설계했고, 이후 프론트엔드와 백엔드를 병렬로 개발했습니다.  
중반부터 문서 AI, 카카오 로그인, 공공데이터 연동을 추가했으며, 마지막에는 통합 테스트와 오류 수정, AWS 배포 및 발표 준비를 진행했습니다.

짧은 기간이었기 때문에 기능별 담당을 명확하게 나누고, 공통 규칙이 필요한 부분은 매일 진행 상황을 공유하며 맞췄습니다.

## 6. 기술 스택
프론트엔드는 React와 Vite를 기반으로 구성했고, React Router로 화면 이동과 권한별 라우팅을 처리했습니다.  
Axios로 백엔드 API와 통신했으며, ESG 지표 시각화에는 Chart.js를 사용했습니다.  

백엔드는 Java 17과 Spring Boot를 사용하고, Spring Security와 JWT로 인증·인가를 구현했습니다.  
데이터 접근은 MyBatis, 영구 데이터 저장은 PostgreSQL, DB 버전 관리는 Flyway를 사용했습니다.

Redis는 Refresh Token, 로그아웃 토큰 블랙리스트, 대시보드 캐시와 중복 실행 방지에 활용했고, WebSocket으로 승인 결과를 실시간 알림으로 전달했습니다.  
최종 배포는 Docker Compose를 기반으로 AWS EC2에서 구성했습니다.

## 7. 시스템 아키텍처
아키텍처는 사용자 화면, React 프론트엔드, Spring Boot 백엔드, 데이터 저장소와 외부 서비스로 구분했습니다.

백엔드는 Controller, Service, Repository의 3계층으로 역할을 분리해 요청 처리, 비즈니스 로직, 데이터 접근 책임이 섞이지 않도록 했습니다.  
업무 원본과 승인 이력은 PostgreSQL에 영구 저장하고, Redis는 인증 상태와 캐시처럼 빠른 처리와 만료가 필요한 데이터에 사용했습니다.

또한 카카오 OAuth2, 문서 AI/OCR, 한국에너지공단과 KOSIS 공공데이터 API를 연동했으며, 전체 서비스는 Docker Compose로 묶어 AWS EC2에 배포했습니다.

## 8. ERD
ERD는 크게 다섯 영역으로 구성했습니다.

첫 번째는 기업, 부서, 사용자, 사업장과 같은 기준정보입니다.  
두 번째는 환경·사회·거버넌스 월별 데이터와 승인 이력입니다.  
세 번째는 원천 지표, 안전보건, 이사회 등 세부 업무 데이터입니다.  
네 번째는 보고서, 감사 로그, 넷제로 활동 데이터이고,  
마지막은 ESG 지표, 배출계수, 목표치와 공통코드 같은 마스터 정보입니다.  

이 구조를 통해 실적값뿐 아니라 누가 등록하고 승인했는지까지 함께 추적할 수 있도록 설계했습니다.

## 9. 업무 흐름도

전체 업무 흐름은 문서 접수, 데이터 등록, 승인, 공개의 네 단계로 구성했습니다.

초기 설계에서는 외부 시스템의 데이터를 스케줄러로 자동 수집하는 방식을 고려했습니다.  
하지만 자동 수집만으로는 각 ESG 수치의 출처와 입력 책임자를 명확하게 확인하기 어렵고, 잘못된 데이터가 들어왔을 때 책임 소재가 불분명해질 수 있다고 판단했습니다.

그래서 최종 시스템에서는 각 공장이나 사업장에서 올라온 실적 문서를 기업 ESG 관리자가 확인하고, 문서 분석 결과를 참고해 ESG 수치를 직접 입력하도록 구성했습니다.  
이때 사용한 원본 문서는 해당 수치의 증빙자료로 함께 등록됩니다.

기업 ESG 관리자가 사업장과 기준연월, 지표값, 증빙문서를 등록한 뒤 승인 요청을 보내면, 시스템 관리자가 입력값과 증빙자료, 처리 이력을 함께 검토합니다.  
검토 결과가 적합하면 최종 승인하고, 문제가 있으면 사유를 작성해 반려합니다. 반려된 데이터는 담당자가 내용을 수정한 뒤 다시 승인 요청할 수 있습니다.

최종 승인된 데이터만 대시보드와 공식 ESG 실적, 보고서에 반영되며, 일반 사용자는 승인 완료된 정보만 조회할 수 있습니다.

즉, 자동 수집의 편의성보다는 입력 담당자와 승인 담당자를 분리하고, 모든 수치에 원본 증빙을 연결해 데이터의 책임성과 신뢰성을 확보하는 방향으로 업무 흐름을 설계했습니다.

## 10. 활용 방안 및 기대 효과
이 플랫폼은 ESG 데이터를 여러 부서의 엑셀이나 문서로 분산 관리하는 문제를 줄이고, 하나의 승인 흐름으로 통합하는 데 활용할 수 있습니다.

본사와 다수 사업장을 운영하는 제조기업에 적용할 수 있으며, 경영진 보고와 투자자·협력사 대상 정보 제공에도 활용 가능합니다.

기대 효과는 네 가지입니다.  
첫째, 승인 이력과 감사 로그를 통해 데이터의 신뢰성과 추적성을 높일 수 있습니다.  
둘째, 자동 수집과 문서 AI 분석으로 반복적인 입력 업무를 줄일 수 있습니다.  
셋째, 공공데이터와 비교해 업종 내 상대적인 효율 수준을 확인할 수 있습니다.  
넷째, 승인 실적을 보고서로 연결해 대외 커뮤니케이션 시간을 단축할 수 있습니다.

## 11. 시스템 관리자 화면 - 구분 슬라이드
지금부터는 권한별 주요 화면을 소개하겠습니다.  
먼저 시스템 관리자 화면입니다.  
시스템 관리자는 사용자와 기업, ESG 지표를 관리하고, 기업 관리자가 요청한 데이터를 최종 승인 또는 반려하며 전체 처리 이력을 확인합니다.

## 12. 사용자·권한 관리
사용자·권한 관리 화면에서는 시스템 내 계정의 소속, 권한과 활성 상태를 관리합니다.

권한은 SYSTEM_ADMIN, COMPANY_MANAGER, EXTERNAL_USER 세 단계로 구성했습니다.  
목록에서 사용자 정보를 조회하고, 상세 화면에서 권한 변경과 계정 활성·비활성 처리를 할 수 있습니다.  
신규 사용자를 등록하면 임시 비밀번호를 안내해 최초 로그인이 가능하도록 구성했습니다.

프론트에서는 권한에 따라 메뉴와 버튼을 제어하고, 백엔드에서도 API 접근 권한을 다시 검증해 화면 우회 접근을 차단했습니다.

## 13. 기업 관리
기업 관리 화면에서는 기업 기본정보와 소속 사업장을 한 화면에서 관리합니다.

사업자번호, 대표자, 업태와 같은 기본정보를 확인할 수 있고, 사업장을 본사와 공장 유형으로 검색할 수 있습니다.  
각 사업장 상세에서는 선택한 기준월의 최종 승인 ESG 실적도 함께 조회할 수 있습니다.

기업과 사업장의 등록·수정 기능은 권한에 따라 구분했으며, 이미 ESG 데이터가 연결된 사업장은 무결성 보호를 위해 바로 삭제할 수 없도록 제한했습니다.

## 14. ESG 지표 관리
이 화면은 플랫폼에서 사용할 ESG 지표의 기준정보를 관리하는 화면입니다.

환경·사회·거버넌스 영역과 정량·정성 유형, 사용 상태를 조건으로 지표를 조회할 수 있습니다.  
등록·수정 화면에서는 지표 코드, 이름, 단위와 데이터 유형을 관리합니다.

지표를 삭제할 때는 확인 절차를 거치도록 해 실수로 기준정보가 삭제되는 것을 방지했습니다.

## 15. ESG 데이터 승인 관리
승인 관리 화면은 시스템 관리자의 핵심 업무 화면입니다.

기업 관리자가 요청한 지표값과 증빙문서를 확인한 뒤 승인 또는 반려할 수 있습니다.  
상단에는 전체 승인 대기 건수와 E·S·G 영역별 건수를 요약해 우선 처리할 항목을 빠르게 확인하도록 했습니다.

최종 승인 시 해당 값은 공식 실적과 ESG 지수 계산에 반영됩니다.  
반려할 때는 사유 입력을 필수로 하고, 모든 처리 과정은 승인 이력에 남도록 구현했습니다.

## 16. 감사 로그 & 연동 모니터링
감사 로그에서는 최종 승인 과정에서 발생한 주요 작업 이력을 조회할 수 있습니다.

처리 일시, 요청자, 승인자, 대상 지표와 작업 내용을 기록하며, 중요한 승인 이력은 DB 트리거에서도 남도록 구성해 추적성을 높였습니다.

연동 모니터링에서는 외부 데이터 수집 실행 시각과 성공·실패 상태, 원본 데이터 처리 결과를 확인할 수 있어 연동 장애 발생 지점을 빠르게 찾을 수 있습니다.

## 17. 기업 관리자 화면 - 구분 슬라이드
다음은 기업 ESG 관리자 화면입니다.  
기업 관리자는 ESG 데이터를 등록하고 증빙을 첨부하며, AI 분석 결과를 검토한 뒤 승인 요청을 보냅니다.  
또한 승인된 실적을 대시보드와 리포트로 활용합니다.

## 18. ESG 종합 대시보드
종합 대시보드는 최종 승인된 데이터만 기준으로 기업의 ESG 현황을 한눈에 보여줍니다.

종합 점수와 환경·사회·거버넌스별 점수, 내부 추정 등급, 월별 추이를 확인할 수 있습니다.  
아래에는 지표별 실제값과 직전 승인월 대비 개선·악화 여부를 표시했습니다.

사업장별 Scope 2, 안전교육 이수율, 산업재해율을 비교할 수 있고, 지도와 사업장 카드를 선택하면 해당 상세 화면으로 이동하도록 연결했습니다.

## 19. 환경·사회·거버넌스 실적
E·S·G 실적 화면은 최종 승인된 확정값을 기준연월과 사업장 조건으로 조회하는 공통 화면입니다.

환경에서는 전력 사용량, 출하액, Scope 2 배출량을 확인합니다.  
사회에서는 산업재해율, 안전교육 이수율, 위험요인 개선 조치율과 퇴사율을 확인합니다.  
거버넌스에서는 이사회 참석률, 사외이사 비율과 윤리교육 이수율을 조회합니다.  

각 실적에 연결된 실제 증빙 PDF는 미리보기와 다운로드가 가능하며, 대시보드에서 지표를 선택하면 동일한 연도·월 조건을 유지한 채 해당 화면으로 이동합니다.

## 20. 외부 공공데이터 비교
===============

외부 공공데이터 비교 화면은 우리 기업의 승인 완료 실적이 동일 업종과 비교했을 때 어느 수준인지를 확인하기 위한 기능입니다.

외부 기준연도로 2021년 자료를 사용한 이유는, 한국에너지공단에서 자동차 신품 부품 제조업 C303의 전력 사용량과 온실가스 배출량을 함께 확인할 수 있는 최신 공통 기준연도가 2021년이었기 때문입니다.

전력 사용량은 한국에너지공단에서, 출하액은 KOSIS에서 가져와야 했기 때문에 정확한 비교를 위해 두 기관의 기준연도를 모두 2021년으로 통일했습니다. 따라서 이 데이터는 현재 실시간 업종 평균이 아니라, 2021년 동일 업종의 공식 공공통계라는 점을 화면에 명확히 표시했습니다.

또한 단순히 전력 사용량이나 온실가스 배출량의 총량만 비교하지 않고, 출하액 1억 원당 사용량과 배출량을 계산했습니다.

기업마다 생산 규모가 다르기 때문에 총량만 비교하면 규모가 큰 기업이 무조건 많은 전력과 탄소를 배출하는 것으로 보일 수 있습니다. 그래서 출하액 1억 원을 만들어내는 데 전력을 얼마나 사용했고, 온실가스를 얼마나 배출했는지를 비교해 실제 생산 효율을 확인하도록 구성했습니다.

이를 통해 우리 기업이 동일 업종보다 전력과 탄소를 효율적으로 관리하고 있는지, 또는 개선이 필요한지를 객관적인 수치로 확인할 수 있습니다.

관리자 권한에서는 외부 공공데이터를 수동으로 다시 동기화할 수 있도록 구현했습니다.

지표를 선택한 뒤 정량값 또는 정성 내용을 입력하고, 실제 증빙 PDF를 첨부합니다.  
작업 중에는 임시 저장할 수 있고, 입력이 완료되면 바로 승인 요청을 보낼 수 있습니다.

상세 화면에서는 등록, 승인 요청, 승인 또는 반려, 재요청까지의 이력을 타임라인으로 확인할 수 있습니다.

## 22. 증빙문서 등록·AI 분석
이 화면은 PDF, Excel, Word 형태의 증빙문서를 업로드하고 AI로 핵심 ESG 항목을 추출하는 기능입니다.

AI는 문서 유형과 분석 영역, 추출 결과의 신뢰도를 함께 제공합니다.  
예를 들어 환경 문서에서는 전력 사용량과 출하액을, 이사회 문서에서는 전체 이사 수와 참석률을 추출해 지표와 연결합니다.

AI 결과를 그대로 확정하지 않고 담당자가 원문과 비교해 검토·수정한 뒤 임시 저장하거나 승인 요청하도록 구성해, 자동화와 데이터 신뢰성을 함께 고려했습니다.

## 23. ESG 실적 조회
ESG 실적 조회 화면에서는 승인 완료된 데이터만 공식 실적으로 조회합니다.

영역과 연도, 월, 지표 조건으로 검색할 수 있고, 최신 값과 단위, 전년 동월 대비 증감률을 카드로 보여줍니다.  
선택한 지표의 월별 추이는 차트로 확인할 수 있으며, 조회 결과는 CSV로 내보낼 수 있습니다.

또한 필요한 값을 클립보드로 복사하거나 리포트 빌더로 바로 이동할 수 있도록 업무 흐름을 연결했습니다.

## 24. ESG 보고서 시스템 - 리포트 빌더

확정 실적 불러오기를 실행하면 영역별 데이터 표와 제목이 자동 생성됩니다.

작성한 보고서는 서버에 저장하고 공개 여부를 설정할 수 있으며, PDF와 Word 형식으로 출력할 수 있습니다.

공개 화면에서는 내부 작성 중 데이터가 아닌, 최종 승인되어 공개 가능한 ESG 정보와 보고서만 제공합니다.

## 26. 랜딩·로그인·회원가입
랜딩 페이지에서는 ESG의 의미와 플랫폼의 주요 업무 흐름을 간단히 소개합니다.

## 29. 리포트 빌더 - 스마트 집계 & 정규식 동적 바인딩
리포트를 자동 생성할 때 지표마다 집계 방식이 다르다는 문제가 있었습니다.

환경 데이터처럼 기간별 값을 합산해야 하는 지표와, 사회 데이터처럼 평균이 필요한 지표를 코드 기준으로 구분하고 reduce 함수를 사용해 각각 계산했습니다.

또한 템플릿 안의 변수를 한 번만 바꾸는 것이 아니라 문서 전체에서 모두 찾기 위해 정규식의 g 플래그를 사용했습니다.  
찾은 값은 단순 문자열이 아닌 스타일이 적용된 HTML로 치환해 보고서 안에서도 읽기 쉽게 표현했습니다.

## 30. 승인 트랜잭션 + Redis 캐시 무효화 + WebSocket 실시간 알림
최종 승인 과정에서는 상태 변경, 승인 이력, 알림 저장, 캐시 삭제가 서로 다른 결과가 되지 않도록 하나의 트랜잭션으로 처리했습니다.

먼저 승인 상태와 이력을 PostgreSQL에 저장하고, 알림 원본도 DB에 남긴 뒤 관련 Redis 대시보드 캐시를 즉시 삭제합니다.  
이후 트랜잭션이 정상적으로 커밋된 다음 WebSocket 알림을 전송합니다.

핵심은 WebSocket 전송 실패가 정상적인 승인 데이터까지 롤백시키지 않도록, 실시간 전송을 커밋 이후로 분리한 점입니다.

## 31. 증빙문서 무결성 검증 + 승인 데이터 정합성 관리
공식 ESG 실적의 신뢰성을 위해 파일과 데이터 상태를 두 단계로 검증했습니다.

먼저 증빙문서 경로를 저장 루트 기준으로 정규화하고, 허용된 경로 안에 있는 실제 일반 파일인지 확인합니다.  
이를 통해 잘못된 경로 요청이나 물리 파일이 삭제된 문서의 다운로드를 차단합니다.

또한 대시보드와 공개 실적 조회에서는 APPROVED 상태만 조회해, 작성 중이나 승인 대기, 반려 데이터가 공식 통계에 포함되지 않도록 했습니다.

## 32. 한국에너지공단·KOSIS API 통합 + 단위 표준화
두 공공기관의 데이터 구조와 단위가 서로 달랐기 때문에, 백엔드에서 표준화 과정을 거쳤습니다.

한국에너지공단에서는 이천이십일 년 씨 삼공삼 업종의 전력 사용량과 온실가스 배출량을 조회하고, 국가통계포털에서는 동일 업종의 출하액 항목인 티 공이 데이터만 선별했습니다.

천 킬로와트시는 메가와트시로, 천 톤 이산화탄소 환산량은 톤 이산화탄소 환산량으로, 그리고 백만 원 단위의 출하액은 억 원 단위로 변환해 우리 기업의 실적과 같은 기준으로 비교했습니다.

특히 월별 원단위를 단순 평균하지 않고, 누적 전력 사용량을 누적 출하액으로 나누어 실제 기업의 전력 효율을 계산했습니다. 탄소 원단위 역시 누적 온실가스 배출량을 누적 출하액으로 나누어 계산했습니다.

## 33. JWT 인증 + Redis 토큰 생명주기 관리
JWT 인증은 서버 확장에 유리하지만, 발급된 토큰을 즉시 무효화하기 어렵다는 문제가 있습니다.

이를 보완하기 위해 Access Token과 Refresh Token을 분리했습니다.  
Refresh Token은 Redis에 14일 TTL로 저장하고, Access Token이 만료되면 Redis의 Refresh Token을 검증한 뒤 재발급합니다.

로그아웃 시 Refresh Token은 즉시 삭제하고, Access Token은 남은 만료시간만큼만 블랙리스트에 저장합니다.  
따라서 로그아웃 토큰을 차단하면서도 Redis에 불필요한 데이터가 계속 쌓이지 않도록 관리했습니다.

## 34. Docker Compose + Flyway 기반 개발환경 공통화
팀원마다 PostgreSQL과 Redis 버전, DB 구조가 달라 발생하는 실행 오류를 줄이기 위해 개발환경을 공통화했습니다.

Docker Compose에서 PostgreSQL 16과 Redis 7.4 이미지를 고정해 모든 팀원이 동일한 버전을 사용하도록 했습니다.  
한 번의 명령으로 필요한 인프라를 실행하고, 볼륨을 사용해 컨테이너를 재실행해도 데이터를 유지하도록 구성했습니다.

DB 구조와 초기 데이터는 Flyway의 버전별 SQL 파일로 관리했습니다.  
애플리케이션 실행 시 마이그레이션이 순서대로 적용되므로 신규 팀원도 동일한 DB 구조를 빠르게 구성할 수 있었습니다.

## 35. 트러블슈팅 & 사후평가 - 구분 슬라이드
이제 개발과 배포 과정에서 실제로 발생한 문제와 해결 과정, 그리고 프로젝트 결과를 말씀드리겠습니다.

## 36. 트러블슈팅 - 기술적 이슈
배포와 인프라 환경에서 세 가지 주요 이슈가 있었습니다.

첫째, 일부 팀원의 Redis 5 환경에서는 카카오 OAuth 일회용 코드를 조회·삭제하는 GETDEL 명령을 지원하지 않아 오류가 발생했습니다.
Redis 이미지를 7.4.9로 고정해 모든 팀원의 환경을 통일했습니다.

둘째, AWS 배포 후 카카오 로그인이 차단됐습니다.  
외부 배포 환경에서는 HTTPS가 필요했기 때문에 AWS 보안그룹의 443 포트를 열고 Nginx에 SSL을 적용해 해결했습니다.

셋째, HTTPS 배포 빌드에서 카카오맵 키가 전달되지 않았습니다.  
비트 환경변수는 런타임이 아니라 빌드 시점에 주입된다는 점을 확인하고, 도커 빌드 아규먼트와 에이알지, 이엔브이 설정을 통해 빌드 과정에 값을 전달했습니다.

이 과정을 통해 로컬 실행과 실제 배포 환경의 차이를 미리 검증하는 것이 중요하다는 점을 배웠습니다.

## 37. Flyway 체크섬 불일치 트러블슈팅 해결
다음은 Flyway 체크섬 불일치 문제입니다.

이미 DB에 적용된 V4 마이그레이션 파일의 내용이 이후 수정되면서, DB에 저장된 체크섬과 현재 파일의 체크섬이 달라졌습니다.  
Flyway 검증이 실패해 애플리케이션 실행이 중단됐고, 그 결과 MyBatis와 인증 필터 오류도 연쇄적으로 나타났습니다.

개발용 DB를 초기화한 뒤 V1부터 마이그레이션을 다시 적용해 환경을 정상화했습니다.  
그리고 이후에는 이미 실행된 SQL 파일을 수정하지 않고, 변경사항을 V5와 V6처럼 새로운 버전으로 추가하는 규칙을 확정했습니다.

핵심 교훈은 실행된 마이그레이션 파일은 변경하지 않고, 항상 새 버전으로 DB 변경 이력을 남겨야 한다는 것입니다.

## 38. 목표 대비 달성도
화면설계서 기준으로 계획한 30개 화면을 모두 개발했습니다.

중간발표에서는 핵심 CRUD와 승인 워크플로우를 중심으로 시연했고,  
최종발표에서는 전체 화면과 문서 AI 분석, 실시간 알림, 공공데이터 비교, 보고서 기능까지 포함한 통합 결과를 완성했습니다.

기획, 개발, 통합 QA와 발표 준비를 총 15일 일정 안에서 진행했으며, 계획한 핵심 범위를 일정 지연 없이 구현했습니다.

## 39. 잘한 점 & 아쉬운 점
잘한 점은 세 가지입니다.

첫째, DRAFT, PENDING, APPROVED로 이어지는 승인 흐름과 감사 로그를 결합해 데이터의 신뢰성과 추적성을 확보했습니다.  
(첫째, 드래프트, 펜딩, 어프루브드로 이어지는 승인 흐름과 감사 로그를 결합해 데이터의 신뢰성과 추적성을 확보했습니다.)  
둘째, 공용 기능과 도메인별 기능을 분리해 병렬로 개발하면서 짧은 기간에도 30개 화면을 완성했습니다.  
셋째, 문서 AI 분석을 단순 추출로 끝내지 않고 담당자 검토와 승인 흐름까지 연결했습니다.  

아쉬운 점도 있습니다.  
일정상 자동화 테스트를 충분히 작성하지 못해 후반 통합 QA에 시간이 집중됐고, 화면 개발과 API 개발을 병행하면서 일부 스펙 변경으로 재작업이 발생했습니다.  
또한 문서 형식에 따라 AI 추출 정확도 차이가 있어, 향후 프롬프트 개선과 테스트 데이터 확대가 필요합니다.

## 40. 팀 회고
마지막으로 팀원별 회고입니다.

김성민은 팀장으로서 일정 관리와 공용 기능 통합을 경험하며, 짧더라도 매일 진행 상황을 공유하는 것이 협업에 큰 도움이 됐다고 느꼈습니다.  
박정은은 사용자와 권한 관리 화면을 개발하면서, 단순해 보이는 기능도 실제 사용자 관점에서 다양한 예외를 고려해야 한다는 점을 배웠습니다.  
홍현민은 승인과 인프라를 담당하며, 보이지 않는 데이터 정합성이 플랫폼 전체의 신뢰도를 결정한다는 점을 체감했습니다.  
조성민은 리포트 빌더를 구현하면서 실적 데이터가 실제 문서로 자동 변환되는 과정을 완성한 것이 가장 큰 성취였다고 정리했습니다.

이번 프로젝트를 통해 각자 맡은 기능뿐 아니라, 서로 다른 기능이 하나의 업무 흐름으로 연결되는 협업 과정을 경험할 수 있었습니다.
